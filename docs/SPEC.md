# SPEC — 채용공고 분석 및 지원 관리 에이전트

> 상태: Spec 초안 v1.2 (2026-10-28, 선호 조건, 비용 관리, 평가 준비 추가) · 프로젝트명: fitcheck · 작성: JJonyeok

## 1. 목적

**IT 직무 공고 전용**이다. 채용공고 하나를 넣으면 **내가 지원할 수 있는 공고인지, 얼마나 맞는지, 무엇이 부족한지**를 판정하고, 지원 결정과 이후 진행 상황까지 관리한다.

- 지금은 공고 하나를 읽고 지원 여부를 판단하고 이력서를 맞추는 데 시간이 오래 걸린다. 개발 전에 이 시간을 측정해두고(§10), 완성 후 다시 측정해 비교한다.
- 1차 사용자는 본인, 이후 취업 준비 중인 동기 몇 명이 써보게 한다.

## 2. 범위

| 포함 | 제외 |
|---|---|
| IT 직무 공고 입력 (텍스트, URL, 이미지) | 비IT 직무 공고 (입력 단계에서 거절) |
| | 채용 사이트 대량 크롤링, 자동 수집 |
| 이미지 공고의 텍스트 추출 | 지원서 자동 제출 |
| 자격 필터, 요건 매칭, 라벨 판정, 선호 조건 표시 | 실제 합격 확률 예측 |
| 사람 확인과 지원 결정 | 여러 사용자 계정, 로그인 |
| 맞춤 이력서 초안 (방향 제안) | 자기소개서 전체 자동 작성 |
| 지원 현황 트래킹, 마감 알림, 재판정 | |

## 3. 전체 흐름

```
[공고 입력]
   │
   ▼
입력 정규화 ──텍스트 충분──▶ 공고 파싱 (같은 원문이면 캐시 사용) ◀── 이미지 추출 ◀──텍스트 부족(이미지 공고)
                                │
                                ▼
                          IT 직무 확인 ──비IT──▶ "IT 직무 공고만 분석할 수 있어요" 후 종료 (저장 안 함)
                                │      └─분류 불확실──▶ ⏸ 사람 확인
                                ▼
                          중복 공고 확인 ──이미 분석한 공고──▶ 기존 기록에 URL 추가 후 종료
                                │
                                ▼
                          추출 신뢰도 확인 ──핵심 필드 불확실──▶ ⏸ 사람 확인
                                │
                                ▼
                            자격 필터 ──자격 미달──▶ 지원 불가로 저장 후 종료
                                │
                                ▼
                       요건 매칭 → 충족률 → 라벨 → 선호 조건 → 보완 포인트
                                │
                                ▼
                         ⏸ 지원 결정 (지원 / 보류 / 미지원 / 보류 조건 인정)
                                │                         └─ 보류 조건 인정 → 자격 필터부터 다시
                                ▼
                       맞춤 이력서 방향 → 지원 기록 저장
```

별도로 돌아가는 작업
- **역량 추출**: 프로젝트 저장소나 README에서 기술 후보를 뽑고 본인이 확인한다 (§7).
- **재판정**: 역량이 바뀌면(자격증 취득, 프로젝트 추가) 결론이 안 난 공고를 다시 판정한다.
- **마감 알림**: 관심, 보류 상태 공고의 마감 3일 전을 알린다.
- **기존 이력 이관**: 이미 지원한 회사 목록을 한 번 가져온다.

## 4. 에이전트 설계 (LangGraph)

### 4.1 왜 LangGraph인가

| 필요한 것 | LangGraph에서 쓰는 기능 |
|---|---|
| 텍스트 공고와 이미지 공고를 다른 경로로 처리 | 조건부 엣지 |
| 불확실한 추출값 확인, 지원 결정에서 멈추고 사람을 기다림 | `interrupt` |
| 멈춘 뒤 나중에 이어서 진행 (사람이 다음 날 결정해도 됨) | 체크포인터 (SQLite), 공고별 `thread_id` |
| 보류 조건을 인정하면 판정부터 다시 | 이전 노드로 돌아가는 엣지 |

### 4.2 판단 분담 원칙

**LLM은 읽고 해석하는 일만, 판정은 규칙 코드가 한다.**

| 일 | 담당 | 이유 |
|---|---|---|
| 공고 문장을 구조화 (경력, 학력, 요건 분리) | LLM | 표현이 공고마다 제각각 |
| 이미지에서 글자 읽기 | 비전 LLM | 한글 공고 이미지, 표, 강조 문구 |
| 지원 가능 여부 (경력, 학력, 마감, 지역 등) | 코드 | LLM이 애매하게 넘기면 지원 가능한 공고를 버리거나 그 반대가 됨. 같은 입력에 항상 같은 결과가 나와야 함 |
| 요건과 내 프로젝트가 맞는지 | LLM + 코드 검증 | 의미 비교는 LLM, 근거 프로젝트 없는 "충족"은 코드가 거부 |
| 충족률, 라벨, 정렬 | 코드 | 기준을 바꿀 수 있고 설명 가능해야 함 |
| 보완 포인트 문장, 이력서 방향 | LLM | 문장 생성 |

### 4.3 노드

| # | 노드 | 종류 | 입력 → 출력 | 실패 시 |
|---|---|---|---|---|
| 1 | `normalize_input` | 코드 (Playwright) | URL/텍스트/이미지 → `normalized_text`, `text_is_sufficient` | 페이지 접근 불가 → 텍스트 붙여넣기 요청 |
| 2 | `collect_images` | 코드 (Playwright) | 본문 영역 원본 이미지 우선, 없으면 전체 스크린샷 | 이미지 없음 → 사람 확인 |
| 3 | `split_images` | 코드 | 긴 이미지를 겹치게 분할 → `image_chunks` | |
| 4 | `vision_extract` | 비전 LLM | 조각별 텍스트 → 합치고 겹친 부분 중복 제거 | |
| 5 | `parse_posting` | LLM (구조화 출력) | 텍스트 → `JobPosting`, 불확실한 핵심 필드는 `low_confidence_fields` | 스키마 검증 실패 → 오류 내용을 넣어 최대 2회 재시도 → 사람 확인 |
| 5-1 | `check_supported` | 코드 | `job_category`가 IT 계열인지 → 아니면 종료 | 분류 불확실 → 사람 확인 |
| 6 | `check_duplicate` | 코드 | `dedup_key`로 기존 기록 조회, 같은 회사 기지원 여부 | 중복 → URL 추가 후 종료 |
| 7 | `human_verify` | ⏸ interrupt | 불확실한 필드를 원본 이미지 해당 부분과 함께 보여주고 수정받음 | |
| 8 | `check_eligibility` | 코드 | 조건별 판정 `ConditionCheck[]`, 사용자 인정(`overrides`) 반영 | |
| 9 | `match_requirements` | 코드 + LLM | 키워드로 후보 프로젝트를 좁힌 뒤 LLM이 matched/partial/missing 판정 | 근거 없는 matched → 코드가 missing으로 강등 |
| 10 | `score` | 코드 | 충족률, 학력 순위, 라벨, 선호 조건 | |
| 11 | `summarize_gap` | LLM | 보완 포인트 한두 문장 | |
| 12 | `decide` | ⏸ interrupt | 지원 / 보류 / 미지원 / 보류 조건 인정 | 보류 조건 인정 → 8번으로 |
| 13 | `draft_resume` | LLM | 공고에 맞는 프로젝트 순서와 설명 방향 | |
| 14 | `save_record` | 코드 | `ApplicationRecord` 저장, 역량 지문 기록 | |

### 4.4 상태

`schemas.GraphState`가 전체 상태다. 노드는 자기 담당 필드만 쓴다. 체크포인터에 공고별로 저장되므로 멈춘 지점에서 이어 갈 수 있다.

### 4.5 비용 관리 (`budget.py`)

| 장치 | 내용 |
|---|---|
| 파싱 캐시 | 공백을 정리한 원문의 해시로 파싱 결과를 저장. URL이 달라도 원문이 같으면 다시 파싱하지 않음. 스키마 버전이 바뀌면 예전 캐시는 쓰지 않음 |
| 호출 상한 | 공고 1건당 LLM 호출 14회 (파싱 1, 매칭 1, 보완 포인트 1, 이력서 방향 1, 이미지 조각 최대 8, 재시도 최대 2). 넘으면 그 자리에서 멈추고 사람 확인 |
| 이미지 조각 상한 | 최대 8조각. 넘으면 앞부분만 읽고 추출 신뢰도 낮음으로 표시 |
| 조기 종료 | 비IT 공고, 중복 공고, 지원 불가 공고는 매칭 전에 끝나므로 파싱 이후 LLM 호출 없음 |

모든 LLM 노드는 호출 전에 `LLMBudget.spend()`를 부르고, 사용량은 상태의 `llm_calls`에 남는다.

### 4.6 매칭 노드 상세

1. 공고 요건의 키워드를 별칭 사전으로 정규화한다 (`React.js`, `리액트` → `React`).
2. `CompetencyDB.skill_index()`로 키워드가 걸리는 프로젝트를 후보로 고른다. 후보가 없으면 LLM에 보내지 않고 missing.
3. LLM은 요건 문장과 후보 프로젝트의 `my_role`, `contributions`만 보고 판정하며, 판정마다 근거 프로젝트 id를 내야 한다.
4. 코드 검증: matched/partial인데 근거 id가 없거나 후보 밖이면 missing으로 바꾼다.
5. 소프트 스킬(`category: soft`)은 판정은 하되 충족률에서 뺀다.

## 5. 판정 규칙

### 5.0 IT 직무 관문 (`filters.check_supported`)

파싱 단계에서 LLM이 **제목이 아니라 담당업무 기준으로** 직무를 분류한다. "마케팅 자동화 개발자"는 개발, "퍼포먼스 마케터"는 마케팅, "SaaS 기술 영업"은 IT영업/고객성공이다.

| 구분 | 분류 |
|---|---|
| 분석 대상: 개발, 기술 | 개발, AI/데이터, AX/자동화, IT인프라/클라우드, 보안, QA/테스트 |
| 분석 대상: 개발이 아닌 IT | 서비스기획/PM/PO, 프로덕트 디자인(UI/UX), 데이터 분석, IT운영/전산, IT컨설팅/프리세일즈, IT영업/고객성공, IT교육/콘텐츠 |
| 거절 (비IT) | 디자인(편집/광고), 마케팅, 영업, 경영지원, 생산/제조, 서비스/운영, 기타 |

- 비IT 공고는 자격 필터, 매칭으로 가지 않고 종료한다. LLM 비용이 파싱 1회로 끝나고, 지원 현황에도 저장하지 않는다.
- 분류가 불확실하면 사람에게 확인받는다. IT 분류 목록은 `schemas.IT_CATEGORIES` 한 곳에서 관리한다.

### 5.1 자격 필터 (`filters.check_eligibility`)

조건마다 통과(✓) / 보류(△) / 탈락(✕) 중 하나로 판정한다. 하나라도 탈락이면 **지원 불가**, 탈락 없이 보류가 있으면 **불합격권**이다.

| 조건 | 탈락 | 보류 |
|---|---|---|
| 마감 | 마감일 지남 | (통과지만 3일 이내면 "마감 임박" 표시, 채용시 마감은 표시) |
| 경력 | 필수 연수 > 내 경력 | 경력직인데 연수 미기재 |
| 학력 | 필수 학력 > 학사 (우대는 탈락 아님) | 요구 전공 불일치 |
| 졸업 | 졸업예정자 한정, 졸업 후 N년 초과 | 졸업일 미입력 |
| 병역 | 군필 또는 면제 요구 + 미필 | |
| 자격증 | 미보유, 또는 취득 예정인데 발표일이 마감 이후 | 취득 예정 (발표일 미입력이거나 마감 전), "관련 자격증" |
| 어학 | 공인 성적 필수 + 성적 없음, 요구 수준이 두 단계 이상 높음 | "이에 준하는 능력" 인정, 요구 수준이 한 단계 높음 |
| 근무지 | 서울, 과천, 성남, 안양 밖 (판교, 분당, 평촌 등 별칭 포함) | 근무지 미기재 |
| 고용형태 | 파트타임, 계약직 | |
| 추출 | | 핵심 필드 추출 신뢰도 낮음 |

**보류 조건 인정**: 사용자가 보류 칩을 "인정됨"으로 바꾸면 그 조건은 통과로 바뀌고 다시 판정한다. 인정 기록은 지원 기록에 남는다.

### 5.2 충족률 (`scoring.build_gap_report`)

- matched = 1, partial = 0.5, missing = 0
- 소프트 스킬은 제외하고 따로 표시
- 계산 기준: 필수요건 → 없으면 우대사항 → 없으면 담당업무
- 셋 다 없으면 계산하지 않음 (None)

### 5.3 라벨 (`filters.fit_band`)

| 라벨 | 색 | 조건 |
|---|---|---|
| 합격권 | 파랑 | 자격 충족, 충족률 80% 이상, 학력에서 불리하지 않음 |
| 안정권 | 주황 | 자격 충족, 충족률 50% 초과 80% 미만. 석사 우대 공고, 충족률 계산 불가 공고는 최대 여기까지 |
| 불합격권 | 빨강 | 충족률 50% 이하, 또는 보류 조건 있음 |
| 지원 불가 | 회색 | 자격 조건 탈락 |

라벨은 합격 확률이 아니라 **공고 요건과의 적합도**다. 트래킹 데이터가 쌓이면 라벨별 실제 서류 통과율을 보고 80%, 50% 기준을 조정한다.

### 5.4 선호 조건 (`preferences.check_preferences`)

"지원할 수 있나"(자격 필터)나 "요건에 맞나"(라벨)가 아니라 **"가고 싶은 곳인가"**를 본다. 라벨에는 반영하지 않고 "선호 2/3"처럼 따로 표시한다. 섞으면 라벨이 요건 적합도라는 의미를 잃는다.

| 조건 | 기본값 | 판정 |
|---|---|---|
| 연봉 | 3,500만원 이상 | 범위의 상한이 기준 이상이면 충족 (협상 여지) |
| 사수 | 있음 | 사수, 시니어, 리드 언급 여부 |
| 회사 단계 | 전부 허용 (Seed ~ 대기업) | 좁히려면 `competencies.local.yaml`에서 지움 |
| 근무 방식 | 제한 없음 | 출근, 하이브리드, 원격 |

공고에 정보가 없으면 "정보 없음(?)"으로 두고 감점하지 않는다. 파싱 LLM에는 **공고에 없는 정보는 추측하지 말고 비워라**고 지시한다.

### 5.5 정렬

라벨 → 학력 순위 (학사 요건 공고 > 학력 무관 > 석사 우대) → 충족률 높은 순.

## 6. 화면

`docs/fit_mockup.html` 기준. 그룹바이 FIT 진단과 비슷한 정보 구조지만 색과 강조 방식은 별도로 정했다.

- **입력**: URL 또는 내용 붙여넣기. 비IT 공고는 "IT 직무 공고만 분석할 수 있어요"와 분류 결과를 안내하고 저장하지 않음
- **목록**: 분석한 공고를 §5.5 순서로 정렬, 라벨 필터, D-day (3일 이내 강조), 필수 충족률, 재판정 필요 표시
- **공고 본문**: 핵심 정보 표, 원문 (이미지 공고는 추출 텍스트와 원본 이미지)
- **FIT 진단 패널**
  - 지원 자격 조건 충족률, 요건 적합도 링 (라벨 + 충족률)
  - 지원 자격 칩 ✓ △ ✕ — 보류 칩을 눌러 "인정됨"으로 변경, 마우스를 올리면 이유
  - 자격 요건(필수), 우대 사항(선호) 칩 — 충족 칩에 근거 프로젝트 태그, 보완 가능한 것은 "보완 가능" 태그
  - 소프트 스킬 요건은 "충족률 제외" 태그로 따로 표시
  - 내 선호 조건 칩 ✓ ✕ ? — "라벨에 반영 안 함" 표시
  - 보완 포인트 (보류가 있으면 "인정을 누르면 다시 판정" 안내)
  - 보류 / 미지원 / 지원 결정 버튼 (§4.3의 12번 노드). 지원 불가면 지원 결정 비활성
  - 같은 회사에 이전 지원 기록이 있으면 배너로 표시
  - 역량이 바뀌었으면 "재판정 필요" 배너
- **지원 현황**: 상태별 목록, 마감 임박 표시, "역량이 바뀌어 재판정 필요" 표시

## 7. 역량 DB

- `competencies.local.yaml` (Git 제외): 내 조건(`constraints`), 선호 조건, 프로젝트 목록. 공개 저장소에는 `competencies.example.yaml`만 올린다. 기술은 반드시 근거 프로젝트에 묶인다.
- **역량 추출**: 저장소나 README를 넣으면 LLM이 기술 후보와 근거 문장(파일 경로)을 뽑고, 본인이 "직접 함 / 팀원이 함 / 조금 만져봄"을 고른다. 팀 프로젝트는 확인 필수, 1인 프로젝트는 일괄 승인 가능. "조금 만져봄"은 매칭에서 partial로만 잡힌다.
- 연락처, 주민번호 같은 개인정보는 넣지 않는다.

## 8. 트래킹

- 상태: 관심 → 지원 → 서류합격 → 면접 → 최종합격 / 탈락, 보류, 미지원
- **중복 공고**: 회사명과 직무명을 정규화한 `dedup_key`로 묶고 플랫폼별 URL을 모은다. 같은 회사의 다른 포지션은 합치지 않는다.
- **기지원 회사 표시**: 포지션이 달라도 같은 회사 지원 기록이 있으면 알린다.
- **재판정**: 판정 당시 역량 지문(`judged_with`)이 현재와 다르면 관심, 보류, 미지원 공고를 다시 판정한다.
- **기존 이력 이관**: 회사, 직무, 상태, 날짜를 CSV로 받아 `imported=true` 기록으로 저장한다. 공고 원문이 없으므로 재판정 대상에서 빠진다.

## 9. 비기능 요구

**수집 원칙**
- 사용자가 넣은 URL 한 건씩만 가져온다. 목록 페이지 순회, 예약 수집은 하지 않는다.
- 로그인이 필요한 페이지는 가져오지 않고 텍스트 붙여넣기를 요청한다.

**보안**
- API 키는 `.env`에만 둔다. `.env.example`만 저장소에 올린다.
- 개인 데이터(`data/`, 지원 이력 DB, 캡처 이미지)는 `.gitignore`로 제외한다.
- 커밋 전에 비밀 값이 들어갔는지 확인한다 (QA 단계 체크리스트).
- 공고 원문은 화면에 그대로 넣지 않고 이스케이프한다 (XSS).

**Git**
- 커밋 작성자와 메시지에는 JJonyeok만 쓴다. 모델명, 도구명은 쓰지 않는다.

## 10. 평가

준비 방법은 `eval/README.md`. 정답셋(`eval/labels.csv`)과 도입 전 시간(`eval/time_log.csv`)은 **개발 시작 전에** 만든다.


| 항목 | 방법 | 목표 |
|---|---|---|
| 도입 전후 시간 | 공고 10개를 손으로 판단하고 이력서 방향 정하는 시간 측정 → 완성 후 같은 방식으로 재측정 | 수치로 비교 |
| 파싱 정확도 | 실제 공고 20개(텍스트 10, 이미지 10)에 정답 표시, 핵심 필드 일치율 측정 | 핵심 필드 90% 이상 |
| 자격 필터 정확도 | 같은 20개에 직접 "지원 가능 여부" 표시 후 비교 | 지원 가능한데 지원 불가로 버린 경우 0건 |
| 사용성 | 동기 3명 이상이 각자 공고 5개씩 사용, 의견 수집 | |
| 규칙 테스트 | `pytest tests/` | 전부 통과 |
