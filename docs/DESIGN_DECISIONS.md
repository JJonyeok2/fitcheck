# DESIGN DECISIONS — fitcheck 설계 원칙과 그 이유

> 작성: JJonyeok · 관련 문서: [SPEC.md](SPEC.md), [AGENT_DESIGN.md](AGENT_DESIGN.md)
> 각 결정마다 **문제, 검토한 대안, 선택과 이유, 치른 대가, 검증 방법**을 적는다.
> 설계를 바꿀 때는 이 문서의 해당 결정을 먼저 고치고, 바꾼 이유를 "변경 이력"에 남긴다.

## 목차

| # | 결정 | 한 줄 요약 |
|---|---|---|
| D1 | LLM은 해석, 판정은 코드 | 같은 공고에는 항상 같은 판정, 이유를 설명할 수 있어야 한다 |
| D2 | 지원 가능한 공고를 버리지 않는다 | 두 종류의 오류 중 "놓치는 오류"가 훨씬 비싸다 |
| D3 | 통과, 보류, 탈락의 3단계 판정 | 공고 문장은 애매한데, 2단계로는 애매함을 표현할 곳이 없다 |
| D4 | 근거 없는 "충족"은 인정하지 않는다 | LLM은 그럴듯하게 맞다고 말한다. 증거가 있어야 믿는다 |
| D5 | 점수 대신 라벨, 라벨은 합격 확률이 아니다 | 정밀해 보이는 숫자는 실제보다 많이 안다고 착각하게 만든다 |
| D6 | 선호 조건은 라벨과 섞지 않는다 | "지원할 수 있나"와 "가고 싶나"는 다른 질문이다 |
| D7 | IT 직무 확인은 입력 단계의 관문이다 | 개인 조건이 아니라 서비스의 범위이기 때문 |
| D8 | 자율 에이전트가 아니라 정해진 그래프 | 이 일은 순서가 정해져 있고, 자유도는 위험만 늘린다 |
| D9 | 사람이 끼어드는 곳은 두 곳뿐 | 확인을 자주 시키면 결국 아무것도 안 읽고 누른다 |
| D10 | 싼 판정을 먼저, 비싼 판정은 나중에 | 걸러질 공고에 LLM 비용을 쓰지 않는다 |
| D11 | 사용자가 넣은 URL 한 건만 가져온다 | 수집은 이 서비스의 핵심이 아니고, 위험은 크다 |
| D12 | 역량은 기술 목록이 아니라 프로젝트 단위 | 면접에서 물어보는 건 "써봤냐"가 아니라 "어디서 뭘 했냐"다 |
| D13 | 개인 정보는 코드와 분리한다 | 공개 저장소와 내 실제 정보가 섞이면 안 된다 |
| D14 | 실제 모델 없이도 개발이 멈추지 않게 | 모델 선택은 늦어질 수 있고, 테스트는 매번 같아야 한다 |

## D1. LLM은 해석, 판정은 코드

**문제**
공고 하나를 보고 "지원할 수 있나"를 정하는 일은 두 가지가 섞여 있다. 하나는 **공고 문장을 읽고 이해하는 일**("경력 3년 이상 또는 이에 준하는 역량"이 무슨 뜻인가), 다른 하나는 **내 조건과 비교해 판단하는 일**(내 경력 0년이면 지원 가능한가)이다.

**검토한 대안**

| 대안 | 장점 | 문제 |
|---|---|---|
| A. 전부 LLM에게 맡김 ("이 공고에 내가 지원할 수 있어?") | 구현이 가장 쉽다 | 같은 공고를 두 번 넣으면 다른 답이 나올 수 있다. 왜 그렇게 판단했는지 추적할 수 없다. 기준(예: 근무지)을 바꿔도 결과가 어떻게 바뀔지 예측할 수 없다 |
| B. 전부 규칙 코드 (정규식, 키워드) | 결정적이고 빠르고 무료 | 공고 표현이 회사마다 제각각이라 읽는 단계에서 무너진다. "3년↑", "3년 이상", "경력 3+"를 다 규칙으로 잡을 수 없다 |
| **C. 읽기는 LLM, 판단은 코드** | 각자 잘하는 일만 한다 | 두 단계 사이의 형식(스키마)을 잘 설계해야 한다 |

**선택과 이유**
C를 골랐다. LLM은 **문장을 구조화된 값으로 바꾸는 데까지만** 쓰고(`JobPosting`), 그 값으로 지원 가능 여부, 충족률, 라벨을 정하는 건 전부 코드(`filters.py`, `scoring.py`)가 한다.

- **재현성**: 같은 `JobPosting`이면 판정은 항상 같다. 판정 규칙 테스트 31개가 이를 보장한다.
- **설명 가능성**: 판정마다 조건별 결과(`ConditionCheck`)가 남아서 "근무지가 수원이라서 지원 불가"처럼 이유를 화면에 그대로 보여줄 수 있다.
- **기준 변경이 안전함**: 희망 지역에 수원을 추가하면 어떤 공고가 바뀔지 정확히 안다. 프롬프트를 고치는 것과 다르게 결과를 예측할 수 있다.
- **오류의 위치가 분명함**: 판정이 틀리면 원인은 둘 중 하나다. 파싱이 틀렸거나(LLM 문제), 규칙이 틀렸거나(코드 문제). 섞여 있으면 어디서 틀렸는지 찾을 수 없다.

**치른 대가**
- 스키마에 없는 조건은 판정할 수 없다. 공고에 새로운 형태의 조건이 나오면 스키마와 규칙을 둘 다 고쳐야 한다.
- LLM이 공고를 잘못 읽으면 코드는 그 잘못된 값으로 정확하게 틀린 판정을 낸다. 그래서 핵심 필드는 추출 신뢰도를 따로 받고(D9), 정답셋으로 파싱 정확도를 측정한다.

**검증**: 정답셋 20개로 파싱 핵심 필드 일치율 90% 이상 (Spec 10장).

## D2. 지원 가능한 공고를 버리지 않는다

**문제**
자격 필터는 두 가지 방향으로 틀릴 수 있다.
- **놓치는 오류**: 지원할 수 있는 공고를 "지원 불가"로 버림
- **헛걸음 오류**: 지원할 수 없는 공고를 "지원 가능"으로 보여줌

**두 오류의 비용 비교**

| | 놓치는 오류 | 헛걸음 오류 |
|---|---|---|
| 사용자가 알아챌 수 있나 | **못 알아챔**. 버려진 공고는 다시 보지 않는다 | 알아챔. 공고를 열어보면 보인다 |
| 잃는 것 | 지원 기회 자체 | 공고를 읽는 몇 분 |
| 되돌릴 수 있나 | 마감되면 못 되돌림 | 언제든 |

**선택과 이유**
놓치는 오류를 거의 0으로 만드는 쪽으로 모든 판정 규칙을 기울였다. 구체적으로:

- **"우대"는 절대 탈락 사유가 아니다**: "석사 우대"는 통과, "석사 이상"만 탈락 (`preferred_only`).
- **애매하면 탈락이 아니라 보류**: "또는 이에 준하는 능력", "관련 자격증", 취득 예정 자격증은 전부 보류 (D3).
- **정보가 없으면 탈락시키지 않는다**: 근무지 미기재는 보류, 연봉 미기재는 "정보 없음"으로 감점 없음.
- **추출이 불확실하면 판정 전에 사람에게 묻는다**: 경력, 학력, 근무지처럼 틀리면 공고를 버리게 되는 필드만 골라서 (`CriticalField`).
- **동네 이름까지 잡는다**: "판교", "평촌"처럼 시 이름 없이 적힌 근무지를 놓치지 않게 별칭 사전을 둔다.

**치른 대가**
목록에 보류, 불합격권 공고가 더 많이 남는다. 대신 이들은 라벨과 정렬로 아래쪽에 가므로, 합격권부터 보는 사용 흐름에는 방해가 적다.

**검증**: 평가 목표를 "정확도 몇 %"가 아니라 **"지원 가능한데 지원 불가로 버린 경우 0건"**으로 따로 잡았다 (Spec 10장). 한 건이라도 나오면 원인을 기록하고 규칙을 고친다.

## D3. 통과, 보류, 탈락의 3단계 판정

**문제**
공고 문장은 애매한 경우가 많다. "TOEIC 800점 이상 또는 이에 준하는 영어 능력"은 성적이 없는 사람에게 지원 자격이 있는가? 공고만 봐서는 알 수 없다.

**검토한 대안**
- **2단계 (통과/탈락)**: 애매한 경우를 어느 한쪽으로 몰아야 한다. 탈락으로 몰면 D2를 어기고, 통과로 몰면 "확인이 필요하다"는 정보가 사라진다.
- **점수 (0~1 확률)**: "0.6 확률로 지원 가능"은 사용자가 무엇을 해야 할지 알려주지 않는다.
- **3단계 (통과/보류/탈락)**

**선택과 이유**
3단계를 골랐다. **보류는 "사람이 확인하면 결론이 나는 것"**이라는 뜻이고, 그래서 행동으로 이어진다.
- 보류 칩마다 이유가 붙는다 ("성적 없이 지원 가능한지 확인").
- 사용자가 확인하고 **인정**을 누르면 통과로 바뀌고 다시 판정된다. 인정 기록은 남는다.
- 보류가 하나라도 남아 있으면 라벨은 불합격권이다. 확인하지 않은 공고가 합격권으로 보이면 안 되기 때문이다.

**치른 대가**
사용자가 보류를 직접 풀어야 하는 수고가 생긴다. 대신 보류는 화면에서 바로 풀 수 있게 했고, 같은 회사의 같은 조건을 반복해서 묻지 않도록 인정 기록을 저장한다.

**자격증 취득 예정의 경우**: 보류로만 두면 실기 발표일이 마감 이후인 공고까지 보류로 남는다. 그래서 발표일을 입력하면 마감일과 비교해 **발표가 마감보다 늦으면 탈락**, 빠르면 보류로 자동 구분한다. 보류를 줄이는 방법은 판단을 미루는 게 아니라 판단에 필요한 정보를 더 받는 것이다.

## D4. 근거 없는 "충족"은 인정하지 않는다

**문제**
"이 사람이 LangChain 요건을 충족하나?"라고 LLM에게 물으면, LLM은 관련 있어 보이는 경험을 찾아 그럴듯하게 "충족"이라고 답하는 경향이 있다. 팀 프로젝트에서 다른 팀원이 쓴 기술도 README에 있으면 내 역량처럼 잡힌다.

**선택과 이유**
- **매칭마다 근거 프로젝트 id를 반드시 내게 한다.** 근거가 없거나, 후보 목록에 없는 프로젝트를 대면 코드가 "미충족"으로 강등한다.
- **LLM에게는 후보 프로젝트만 보여준다.** 키워드로 걸리는 프로젝트를 코드가 먼저 고르고, 후보가 없으면 LLM을 아예 부르지 않고 미충족으로 처리한다. LLM이 볼 수 없는 것은 지어낼 수도 없다.
- **프로젝트에서 "내가 한 일"만 넘긴다** (`my_role`, `contributions`). 팀 전체 스택은 넘기지 않는다.
- **"조금 만져봄"은 부분 충족(0.5)까지만**: 역량 추출 단계에서 본인이 숙련도를 고른다.

**이유**
이 서비스의 결과는 이력서와 면접으로 이어진다. 충족률이 부풀려지면 지원은 늘겠지만, 면접에서 "이 프로젝트에서 LangChain을 어떻게 썼어요?"에 답하지 못한다. **매칭 결과가 곧 면접에서 말할 수 있는 근거여야 한다.** 화면에서 충족 칩마다 근거 프로젝트 태그를 붙이는 것도 같은 이유다.

**치른 대가**
실제로는 할 수 있는데 프로젝트로 증명이 안 되는 역량은 미충족으로 나온다. 이건 버그가 아니라 의도다. 갭 리포트가 "이 역량은 근거 프로젝트가 없다"고 알려주는 것 자체가 보완 방향이 된다.

## D5. 점수 대신 라벨, 라벨은 합격 확률이 아니다

**문제**
그룹바이 같은 서비스는 "서류 합격 가능성 8.8/10"처럼 소수점 점수를 보여준다. 이 서비스도 충족률 숫자를 그대로 보여줄 수 있다.

**선택과 이유**
- **소수점 점수를 쓰지 않는다.** 8.8과 8.6의 차이는 의미가 없는데, 숫자는 그 차이가 의미 있는 것처럼 보이게 한다. 실제로 아는 것보다 정밀하게 말하는 셈이다.
- **4단계 라벨**: 합격권(80% 이상), 안정권(50% 초과 80% 미만), 불합격권(50% 이하 또는 보류 있음), 지원 불가(자격 미달). 사용자가 할 행동이 라벨마다 다르다. 합격권은 바로 지원, 안정권은 보완 포인트 확인, 불합격권은 보류 확인 또는 넘김, 지원 불가는 안 봄.
- **라벨은 "공고 요건과의 적합도"라고 화면에 명시한다.** 합격 여부는 지원자 수, 회사 사정, 서류 완성도에 달려 있고, 이 서비스는 그걸 모른다. 모르는 것을 아는 척하지 않는다.

**치른 대가와 아직 검증 안 된 가정**
80%, 50%라는 경계는 **근거가 없는 초기값**이다. 부분 충족을 0.5로 친 것도 마찬가지다. 그래서 지원 결과(서류 합격, 탈락)를 트래킹하고, 데이터가 쌓이면 라벨별 실제 서류 통과율을 보고 경계를 조정한다. 경계값은 `filters.py` 상수 두 개(`PASS_COVERAGE`, `STABLE_COVERAGE`)에만 있어서 바꾸기 쉽다.

## D6. 선호 조건은 라벨과 섞지 않는다

**문제**
연봉, 사수 유무, 회사 단계도 지원을 결정하는 데 중요하다. 이걸 라벨 계산에 넣으면 한 화면에서 다 볼 수 있을 것 같다.

**선택과 이유**
섞지 않고 "선호 2/3"처럼 따로 보여준다.
- **질문이 다르다**: 라벨은 "이 회사가 나를 원할 만한가"(요건 적합도), 선호는 "내가 이 회사를 원하나"다. 섞으면 합격권 공고가 연봉 때문에 안정권으로 떨어졌는지, 요건이 부족해서 떨어졌는지 구분할 수 없다.
- **정보가 없는 경우가 많다**: 연봉은 "회사 내규"가 흔하다. 이걸 라벨에 넣으면 정보 없음을 감점할지 말지 정해야 하는데, 어느 쪽이든 라벨이 왜곡된다. 따로 두면 "?"로 표시하고 끝낼 수 있다.
- **선호는 사람마다, 시기마다 바뀐다**: 바꿔도 라벨과 재판정에 영향이 없어야 한다.

**치른 대가**: 화면에 볼 것이 하나 늘었다. 그래서 선호 영역에 "라벨에 반영 안 함"이라고 적어둔다.

## D7. IT 직무 확인은 입력 단계의 관문이다

**문제**
처음에는 "IT 직무만"을 자격 필터의 한 조건(직무 불일치 → 지원 불가)으로 넣었다.

**바꾼 이유**
- **범위의 문제지 자격의 문제가 아니다**: 마케팅 공고에 "지원 불가"라고 저장하면, 마치 내가 자격이 없어서 못 가는 것처럼 기록된다. 사실은 이 서비스가 그 공고를 다루지 않는 것이다.
- **비용**: 자격 필터까지 가면 이미 관문 노드들이 돈다. 파싱 직후에 끊으면 파싱 1회로 끝난다.
- **기록 오염**: 비IT 공고가 지원 현황에 쌓이면 통계(라벨별 서류 통과율)가 흐려진다. 그래서 저장도 하지 않는다.

**분류 기준을 "담당업무"로 정한 이유**
제목만 보면 "AI 마케팅 매니저"는 IT처럼 보이고 "개발 문화 담당자"는 개발처럼 보인다. 실제로 하는 일을 기준으로 해야 "마케팅 자동화 개발자"는 개발로 받고 "퍼포먼스 마케터"는 거절할 수 있다. 개발이 아닌 IT 직무(기획, UI/UX, 데이터 분석, IT운영, IT영업, IT교육)도 포함하는데, 경계는 "담당업무가 IT 서비스, 시스템, 데이터를 직접 다루는가"다.

## D8. 자율 에이전트가 아니라 정해진 그래프

**문제**
"에이전트"라고 하면 LLM이 도구를 골라 쓰며 스스로 다음 행동을 정하는 방식(ReAct 등)을 떠올리기 쉽다.

**검토한 대안**

| 대안 | 문제 |
|---|---|
| A. 자율 에이전트 (LLM이 다음 단계 선택) | 공고마다 실행 경로가 달라져서 재현과 디버깅이 어렵다. LLM이 "자격 필터를 건너뛰자"고 판단할 수 있다. 호출 수를 예측할 수 없어 비용 상한을 걸기 어렵다 |
| B. 함수를 순서대로 호출하는 스크립트 | 사람 확인에서 멈췄다가 다음 날 이어가는 기능을 직접 만들어야 한다. 분기와 되돌아가기가 늘어나면 코드가 엉킨다 |
| **C. LangGraph로 정해진 그래프** | 분기와 순서는 코드가 정하고, 멈춤과 재개는 프레임워크가 처리 |

**선택과 이유**
이 일은 **순서가 이미 정해져 있다**: 읽고 → 거르고 → 비교하고 → 사람이 정한다. LLM에게 순서를 정하게 할 이유가 없고, 자유도를 주면 D1(재현성)과 D10(비용 통제)을 지킬 수 없다.

LangGraph를 고른 건 이 그래프에 필요한 네 가지를 기본으로 주기 때문이다.
- **조건부 분기**: 텍스트 공고와 이미지 공고의 경로
- **interrupt**: 사람 확인, 지원 결정에서 멈추기
- **체크포인터**: 멈춘 상태를 저장해 며칠 뒤 이어가기
- **되돌아가는 엣지**: 보류 인정 후 자격 필터부터 다시

**분기 함수는 상태만 보는 순수 함수로 만든다.** LLM이 분기를 정하지 않으므로, 모든 경로를 단위 테스트로 확인할 수 있다 (경로 테스트 8개).

## D9. 사람이 끼어드는 곳은 두 곳뿐

**문제**
사람 확인은 정확도를 올리지만, 너무 자주 물으면 사용자는 읽지 않고 "확인"을 누르게 된다. 그러면 확인 단계는 있지만 실제로는 아무것도 확인하지 않는 상태가 된다.

**선택과 이유**
- **사람 확인 (`human_verify`)**: 틀리면 공고를 버리게 되는 **핵심 필드가 불확실할 때만** (D2). 모든 필드가 아니라 경력, 학력, 근무지, 고용형태, 자격증, 어학, 직무 분류만. 이미지 공고면 원본 이미지의 해당 부분을 잘라 같이 보여줘서 판단하기 쉽게 한다.
- **지원 결정 (`decide`)**: 지원은 사람이 해야 하는 결정이다. 서비스가 대신 정하지 않는다.
- **무한 반복 방지**: 같은 공고에서 사람 확인은 최대 2회. 그 다음은 사람이 고친 값을 믿고 진행한다.

**치른 대가**: 확인 대상이 아닌 필드(예: 우대사항 문장)의 파싱 오류는 사람이 못 잡는다. 이런 오류는 라벨에 주는 영향이 작고, 정답셋 평가로 따로 측정한다.

---

## D10. 싼 판정을 먼저, 비싼 판정은 나중에

**문제**
LLM 호출은 공고마다 비용과 시간이 든다. 특히 이미지 공고는 조각 수만큼 비전 호출이 나간다.

**선택과 이유**
그래프 순서를 **비용이 낮고 걸러내는 힘이 큰 것부터** 배치했다.

```
파싱(LLM 1회) → IT 확인(코드) → 중복(코드) → 자격 필터(코드) → 매칭(LLM) → 보완 포인트(LLM)
```

- 비IT, 중복, 마감, 지역, 경력 미달 공고는 매칭 전에 끝나서 **파싱 이후 LLM 비용이 0**이다.
- 같은 원문은 해시로 캐시해서 다시 파싱하지 않는다. URL이 달라도 원문이 같으면(플랫폼 간 중복) 재사용한다.
- 공고 1건당 LLM 호출 상한 14회, 이미지 조각 상한 8개. 넘으면 계속 쓰는 대신 멈추고 사람에게 넘긴다. **비용이 예측 가능해야 동기들에게도 써보라고 할 수 있다.**
- 재판정은 저장된 파싱 결과를 쓰므로 파싱 비용이 다시 들지 않는다.

**치른 대가**: 자격 필터에서 지원 불가가 나오면 매칭 결과(무엇이 부족한지)를 볼 수 없다. 지원할 수 없는 공고의 갭을 보는 것은 가치가 낮다고 판단했다.

## D11. 사용자가 넣은 URL 한 건만 가져온다

**문제**
채용 사이트를 주기적으로 크롤링하면 공고를 일일이 넣지 않아도 된다.

**선택과 이유**
하지 않는다.
- **핵심이 아니다**: 이 서비스의 가치는 "공고를 찾아주는 것"이 아니라 "찾은 공고를 판정하는 것"이다. 공고 탐색은 이미 사람인, 원티드, 그룹바이가 잘한다.
- **위험이 크다**: 대량 수집은 사이트 이용약관과 충돌할 수 있고, 차단되면 서비스 전체가 멈춘다. 사이트 구조가 바뀔 때마다 고쳐야 한다.
- **로그인이 필요한 페이지는 가져오지 않는다**: 대신 내용을 붙여넣게 한다. 내 계정 정보를 서비스에 넣지 않기 위해서다.

**치른 대가**: 공고를 직접 넣는 수고가 남는다. 대신 그 수고는 "이 공고를 볼지 말지 내가 이미 한 번 골랐다"는 의미이기도 하다.

## D12. 역량은 기술 목록이 아니라 프로젝트 단위

**문제**
역량을 `[Python, React, AWS, ...]` 같은 기술 목록으로 저장하면 매칭이 간단하다.

**선택과 이유**
프로젝트를 단위로 저장하고, 기술은 프로젝트 안에 넣는다 (`Project.skills`).
- **근거가 붙는다**: D4를 가능하게 하는 구조다. 기술 목록만 있으면 "어디서 썼는지"를 답할 수 없다.
- **팀 프로젝트 구분**: 프로젝트마다 `my_role`, `team_size`를 두고, 내가 직접 한 기술만 넣는다. 6인 팀 프로젝트의 RAG 파이프라인을 내가 안 만들었으면 내 역량에 넣지 않는다.
- **이력서로 바로 이어진다**: 맞춤 이력서 방향(`draft_resume`)이 "어떤 프로젝트를 앞에 두고 무엇을 강조할지"를 프로젝트 단위로 제안할 수 있다.

**치른 대가**: 처음 입력하는 데 시간이 든다. 그래서 저장소나 README에서 후보를 뽑고 본인이 확인만 하는 역량 추출 기능(T13)을 둔다.

## D13. 개인 정보는 코드와 분리한다

**문제**
저장소는 공개다. 그런데 판정에는 졸업일, 병역, 프로젝트, 희망 연봉 같은 내 정보가 필요하다.

**선택과 이유**
- 내 실제 정보는 `competencies.local.yaml`, 공개용은 가상 데이터로 채운 `competencies.example.yaml`. 코드는 local이 있으면 local, 없으면 예시를 읽는다.
- **테스트는 항상 예시 파일 기준**으로 돌린다. 내 정보를 바꿔도 테스트 결과가 바뀌지 않고, 다른 사람이 clone해도 같은 결과가 나온다.
- API 키는 `.env`, 지원 이력 DB와 캡처 이미지는 `data/`. 전부 `.gitignore`로 제외하고, 커밋 전에 비밀 값 검사를 한다 (T1).
- 로그에는 공고 원문 대신 해시만 남긴다.

**치른 대가**: 파일이 둘이라 예시 파일의 구조를 바꾸면 local 파일도 같이 맞춰야 한다. 스키마(Pydantic)가 불러올 때 검사하므로 어긋나면 바로 알 수 있다.

## D14. 실제 모델 없이도 개발이 멈추지 않게

**문제**
어떤 LLM과 비전 모델을 쓸지는 실제 공고로 비교해봐야 정할 수 있다 (Spec 12장). 모델이 정해질 때까지 LLM 노드 개발을 미루면 일정이 밀린다. 또 실제 모델로 테스트하면 매번 결과가 다르고 비용이 든다.

**선택과 이유**
- LLM 호출을 **공급자에 의존하지 않는 인터페이스** 하나로 감싸고(`llm.py`), 테스트에서는 미리 정한 응답을 돌려주는 `FakeLLM`을 쓴다.
- 그래서 모든 LLM 노드의 정상, 형식 오류, 근거 없는 출력 경우를 **결정적으로** 테스트할 수 있다.
- 실제 모델은 정답셋 평가(T17)에서만 쓴다. "코드가 맞나"(테스트)와 "모델이 잘 읽나"(평가)를 분리한 것이다.

**치른 대가**: FakeLLM 테스트가 통과해도 실제 모델이 잘 읽는다는 보장은 없다. 그 부분은 정답셋 평가가 맡는다.
