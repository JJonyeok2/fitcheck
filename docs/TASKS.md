# TASKS — fitcheck 구현 작업 목록

> 기준 문서: [SPEC.md](SPEC.md) v1.2 · 작성: JJonyeok
> 진행 방식: Spec → **Task** → Impl → QA → 직접 사용해 보며 최종 검증

## 읽는 법

- 각 Task는 **Impl Agent에게 그대로 넘기는 작업 지시**다. 한 Task는 한 PR, 하루 이내 분량을 목표로 한다.
- **파트**: 이 Task가 Spec의 어느 부분인지 (입력, 파싱, 판정, 매칭, 에이전트, 저장, API, 화면, 평가, QA)
- **완료 조건**을 모두 만족해야 완료다. 테스트 없이 완료 처리하지 않는다.
- LLM을 부르는 코드는 전부 **가짜 LLM(FakeLLM)으로 테스트**한다. 실제 모델이 정해지기 전에도 개발이 멈추지 않게 하기 위해서다.
- 커밋 작성자는 JJonyeok, 메시지에 모델명이나 도구명은 쓰지 않는다. 커밋 전에 `.env`, API 키가 들어가지 않았는지 확인한다.
- **Red → Green**: 모든 Impl Task는 구현 전에 완료 조건을 테스트로 먼저 쓴다.
  1. 테스트 작성 → 실행해서 **실패(Red)** 확인 → `test: ... (Red)`로 커밋
  2. 구현 → 실행해서 **통과(Green)** 확인 → `feat: ... (Green)`으로 커밋
  3. 테스트는 "막혔다", "통과했다"만 보지 말고 **왜 그렇게 됐는지**까지 확인한다 (T1에서 설치 실패를 "차단 성공"으로 착각한 사례)
  4. Green 뒤에 구현을 일부러 망가뜨려 테스트가 실패하는지 확인한다 (테스트가 실제로 잡아내는지)

### U2. 도입 전 시간 재기 — 파트: 평가 ✅ 측정 완료 (2026-10-28)
- 정답셋 중 10개로 `eval/time_log.csv`에 `phase=before` 기록.
- **필요한 시점**: 개발 시작 전. 만든 뒤에 재면 내가 만든 판정 기준에 익숙해져서 수치가 왜곡된다.
- 실제로는 T10까지 개발한 뒤(2026-10-28) 시작했다. 판정 기준 설계에 참여한 뒤라 직접 판단이 빨라졌을 수 있어 기록 메모에 '설계 참여 후 측정'을 남긴다. 측정 도우미: `uv run fitcheck-time start|stop` (`fitcheck/timelog.py`, 테스트 8개, 일부러 넣은 버그 8개 모두 검출)
- 결과: 텍스트 공고 10개, 평균 0.78분 (중앙값 0.8, 최소 0.3, 최대 1.3). 10개 중 9개를 불합격권, 1개를 합격권으로 판단. 지원 불가는 0개
- 주의: 대부분 불합격권이라 '이력서 프로젝트 순서 정하기'까지 간 공고가 거의 없다. 이 수치는 사실상 '빠른 거르기' 시간이라, 완성 후 측정(phase=after)도 같은 범위로 비교해야 한다
