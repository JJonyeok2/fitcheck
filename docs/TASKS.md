# TASKS — fitcheck 구현 작업 목록

> 기준 문서: [SPEC.md](SPEC.md) v1.2 · 작성: JJonyeok
> 진행 방식: Spec → **Task** → Impl → QA → 직접 사용해 보며 최종 검증

## 읽는 법

- 각 Task는 **Impl Agent에게 그대로 넘기는 작업 지시**다. 한 Task는 한 PR, 하루 이내 분량을 목표로 한다.
- **파트**: 이 Task가 Spec의 어느 부분인지 (입력, 파싱, 판정, 매칭, 에이전트, 저장, API, 화면, 평가, QA)
- **완료 조건**을 모두 만족해야 완료다. 테스트 없이 완료 처리하지 않는다.
- LLM을 부르는 코드는 전부 **가짜 LLM(FakeLLM)으로 테스트**한다. 실제 모델이 정해지기 전에도 개발이 멈추지 않게 하기 위해서다.
- 커밋 작성자는 JJonyeok, 메시지에 모델명이나 도구명은 쓰지 않는다. 커밋 전에 `.env`, API 키가 들어가지 않았는지 확인한다.

## M1 텍스트 공고 한 건이 끝까지 판정된다 (1주차)

### T1. 개발 환경과 CI — 파트: QA
**지시**
- `uv`로 의존성 관리 전환, `uv.lock` 커밋. 버전은 Spec 11장 표 기준.
- `ruff`(lint, format) 설정을 `pyproject.toml`에 추가.
- GitHub Actions: push, PR마다 `ruff check`, `pytest` 실행.
- 커밋 전 비밀 값 검사: `pre-commit` + `gitleaks` 훅. `.env`, `competencies.local.yaml`이 스테이징되면 커밋 거부.

**완료 조건**
- [ ] `ruff check .` 통과
- [ ] Actions에서 기존 테스트 31개 통과
- [ ] 가짜 키(`sk-test...`)를 넣은 파일을 커밋하려 하면 거부되는 것 확인

### T2. LLM 클라이언트 — 파트: 파싱, 에이전트
**지시**
- `fitcheck/llm.py`: 공급자에 의존하지 않는 인터페이스.
  - `structured(prompt, schema: type[BaseModel], images=None) -> BaseModel`
  - 호출 전 `LLMBudget.spend()` 필수. 응답 시간, 입력과 출력 토큰 수를 기록.
- 실제 공급자 구현은 OpenAI 하나 (Spec 11.3). 키는 `.env`의 `OPENAI_API_KEY`. 모델 id는 설정으로 (`gpt-6-luna` 기본). 텍스트용과 이미지용 공급자를 설정으로 따로 지정 가능하게.
- 호출마다 토큰 수를 기록하고 `pricing.yaml` 단가로 **누적** 비용 계산 (달러). $20 경고, $27 새 분석 차단, 재판정과 보류 인정은 허용 (Spec 11.4).
- 테스트에서는 실제 공급자를 절대 부르지 않도록, 키가 있어도 `FIT_LLM=fake` 환경에서는 FakeLLM만 쓰게.
- 오류 코드별 안내 (401, 사용 한도 429, `credit_balance_exhausted`)는 Spec 11.3 목록대로.
- `FakeLLM`: 미리 넣어둔 응답을 순서대로 돌려주는 테스트용 구현.
- `scripts/compare_models.py`: U3용. 이미지 공고 N개를 모델별로 파싱해 정답셋과 비교한 표를 출력.

**완료 조건**
- [ ] 키가 없으면 실행 즉시 명확한 오류 메시지 (키 값은 로그에 절대 출력 안 함)
- [ ] 상한 초과 시 `BudgetExceeded`가 나는 테스트
- [ ] `FakeLLM`으로 구조화 출력 검증 실패 → 재시도 동작 테스트

### T3. 저장소 (SQLite) — 파트: 저장
**지시**
- `fitcheck/store.py`: 테이블 `postings`(파싱 결과, 원문 해시, 출처 URL들), `records`(ApplicationRecord), `overrides`.
- 파싱 캐시(`budget.ParseCache`)를 같은 DB 파일로 합침. DB 경로는 `data/fitcheck.sqlite`.
- 스키마 버전 테이블을 두고, 버전이 다르면 마이그레이션 함수 실행.

**완료 조건**
- [ ] 기록 저장 → 다시 열어 읽기 왕복 테스트
- [ ] `dedup_key`로 조회, 회사 단위 기지원 조회 테스트
- [ ] `data/`가 Git에 안 올라가는 것 확인

### T4. 공고 파싱 노드 (텍스트) — 파트: 파싱
**지시**
- `fitcheck/nodes/parse.py`: 텍스트 → `JobPosting`.
- 프롬프트 원칙: 공고에 없는 정보는 추측하지 말고 비울 것. 필수와 우대를 반드시 구분. `job_category`는 **제목이 아니라 담당업무 기준**. 확신이 낮은 핵심 필드는 `low_confidence_fields`에 넣을 것.
- 같은 원문 해시가 캐시에 있으면 LLM을 부르지 않음.
- 스키마 검증 실패 시 오류 내용을 넣어 최대 2회 재시도, 그래도 실패하면 사람 확인으로 넘김.

**완료 조건**
- [ ] `FakeLLM` 기반 단위 테스트: 정상, 재시도 후 성공, 재시도 소진
- [ ] 캐시 적중 시 LLM 호출 0회 테스트
- [ ] (U1 이후) 텍스트 공고 10개 실제 파싱, 핵심 필드 일치율 기록

### T5. 입력 정규화 — 파트: 입력
**지시**
- `fitcheck/nodes/normalize.py`
  - 텍스트: 그대로.
  - URL: Playwright로 렌더링 후 본문 텍스트 추출. 로그인 페이지로 리다이렉트되면 중단하고 "텍스트를 붙여넣어 주세요" 반환.
  - `text_is_sufficient`: 본문 글자 수와, 본문 영역에서 큰 이미지가 차지하는 비율로 판단.
- 사용자가 넣은 URL 한 건만 가져온다. 링크를 따라가거나 목록을 순회하지 않는다.

**완료 조건**
- [ ] 로컬 HTML 고정 파일(텍스트 공고, 이미지 공고, 로그인 페이지) 3종으로 테스트
- [ ] 이미지 위주 공고에서 `text_is_sufficient=False`

### T6. 판정 노드 연결 — 파트: 판정
**지시**
- 이미 구현된 규칙을 노드로 감싼다: `check_supported`, `check_duplicate`, `check_eligibility`.
- `check_duplicate`는 T3 저장소를 사용. 중복이면 기존 기록에 URL만 추가.

**완료 조건**
- [ ] 비IT 공고 → 종료, 저장 안 됨
- [ ] 같은 공고 두 번 → 두 번째는 URL만 추가되고 판정 노드 미실행
- [ ] 마감 지난 공고 → 지원 불가로 저장, 매칭 노드 미실행

### T7. 그래프 골격과 CLI — 파트: 에이전트
**지시** (설계: [AGENT_DESIGN.md](AGENT_DESIGN.md) 2, 4, 5, 6, 12장)
- `fitcheck/graph.py`: LangGraph `StateGraph`. Spec 4.3의 노드 순서와 조건부 엣지. 아직 없는 노드(이미지, 매칭 등)는 통과만 하는 자리표시자.
- SQLite 체크포인터, 공고마다 `thread_id`.
- `interrupt` 2곳: `human_verify`, `decide`.
- CLI: `fitcheck analyze <url|파일>`, `fitcheck resume <thread_id> --decision apply|skip|hold`, `fitcheck override <thread_id> <조건 id>`.

**완료 조건**
- [ ] 텍스트 공고 한 건이 입력부터 `decide` 대기까지 진행 (FakeLLM)
- [ ] 프로세스를 끈 뒤 `resume`으로 이어서 진행
- [ ] 보류 조건 `override` → 자격 필터부터 다시 판정되어 라벨이 바뀌는 테스트

**M1 끝**: 텍스트 공고를 CLI에 넣으면 라벨과 조건별 판정이 나오고, 결정을 기다린다.

## M2 이미지 공고, 매칭, 지원 관리 (2주차)

### T8. 이미지 공고 경로 — 파트: 입력, 파싱
**지시**
- `collect_images`: 본문 영역 원본 이미지 우선, 없으면 전체 스크린샷.
- `split_images`: 세로로 긴 이미지를 겹치게 분할, 최대 8조각 (`cap_image_chunks`).
- `vision_extract`: 조각별 텍스트 추출 후 이어 붙이고 겹친 줄 중복 제거.
- 이후는 T4 파싱 노드로 합류.

**완료 조건**
- [ ] 고정 이미지 파일로 분할 개수, 겹침 테스트
- [ ] 8조각 초과 시 잘리고 추출 신뢰도 낮음 표시
- [ ] (U1 이후) 이미지 공고 10개 핵심 필드 일치율 기록

### T9. 요건 매칭 — 파트: 매칭
**지시**
- `fitcheck/aliases.py`: 기술 별칭 사전 (`React.js`, `리액트` → `React` 등).
- `match_requirements` 노드 (Spec 4.6)
  1. 요건 키워드 정규화
  2. `skill_index()`로 후보 프로젝트 선정, 후보 없으면 LLM 없이 missing
  3. LLM은 요건과 후보 프로젝트의 `my_role`, `contributions`만 보고 **충족 정도 5단계**(Spec 5.2)와 근거 id를 냄
  3-1. 코드가 상한 적용: 팀 프로젝트에서 본인 역할에 없으면 "팀에서 담당"까지, "조금 만져봄" 기술은 0.3까지
  4. 근거 없는 matched/partial은 코드가 missing으로 강등
- 필수와 우대가 모두 없으면 담당업무를 요건처럼 매칭 (Spec 5.2).

**완료 조건**
- [ ] 후보가 없는 요건은 LLM 호출 0회
- [ ] LLM이 근거 없이 matched를 내도 missing으로 바뀌는 테스트
- [ ] 팀 프로젝트에서 내가 안 한 기술은 매칭되지 않는 테스트

### T10. 점수, 선호, 보완 포인트 — 파트: 판정
**지시**
- `score` 노드: `build_gap_report`(가중 적합도) → `education_tier` → `fit_band` → `check_preferences`.
- `summarize_gap` 노드: 보완 포인트 1~2문장. 숫자와 라벨은 코드가 넘긴 값만 쓰도록 프롬프트에 고정.

**완료 조건**
- [ ] 라벨 4종이 각각 나오는 고정 입력 테스트
- [ ] 보완 포인트에 코드가 넘기지 않은 수치가 나오지 않는지 검사

### T11. 맞춤 이력서 방향 — 파트: 에이전트
**지시**
- `draft_resume` 노드: 공고 요건 기준으로 프로젝트 순서와 각 프로젝트에서 강조할 문장 방향 제안.
- 역량 DB에 없는 경험을 만들어내지 않는다. 모든 제안 문장에 근거 프로젝트 id를 붙인다.

**완료 조건**
- [ ] 근거 id가 역량 DB에 없는 제안은 제거되는 테스트

### T12. 지원 기록과 관리 기능 — 파트: 저장
**지시**
- `save_record` 노드: 기록 저장, `judged_with`에 역량 지문.
- `fitcheck rejudge`: 역량 지문이 바뀐 공고 다시 판정.
- `fitcheck due`: 3일 이내 마감인 관심, 보류 공고 목록.
- `fitcheck import <csv>`: 기존 지원 이력 이관 (`imported=true`).
- `fitcheck status <record> <상태>`: 상태 변경과 이력 기록.

**완료 조건**
- [ ] 자격증 추가 → `rejudge` → 해당 공고 라벨이 바뀌는 테스트
- [ ] 이관한 기록은 재판정 대상에서 빠지는 테스트

### T13. 역량 추출 — 파트: 매칭
**지시**
- `fitcheck skills extract <README 또는 폴더>`: 기술 후보와 근거 문장(파일 경로) 추출.
- 후보마다 "직접 함 / 팀원이 함 / 조금 만져봄"을 묻고 `competencies.local.yaml`에 반영. "조금 만져봄"은 매칭에서 partial로만.
- 1인 프로젝트는 일괄 승인 옵션.

**완료 조건**
- [ ] "팀원이 함"으로 고른 기술은 yaml에 들어가지 않는 테스트
- [ ] 기존 yaml의 주석과 순서가 보존됨

**M2 끝**: 이미지 공고도 판정되고, 요건마다 근거 프로젝트가 붙고, 지원 기록이 관리된다.

## M3 화면과 평가 (3주차)

### T14. API 서버 — 파트: API
**지시**
- FastAPI
  - `POST /analyze` (URL 또는 텍스트 또는 이미지 업로드) → `thread_id`, 진행 상태
  - `GET /postings`, `GET /postings/{id}`
  - `POST /postings/{id}/override`, `POST /postings/{id}/decision`, `POST /postings/{id}/verify`
  - `PATCH /records/{id}/status`
- 로컬 전용: `127.0.0.1`에만 바인딩. 업로드 크기와 파일 형식 제한.

**완료 조건**
- [ ] 엔드포인트별 테스트 (FakeLLM)
- [ ] 이미지가 아닌 파일 업로드 거부 테스트

### T15. 공고 진단 화면 — 파트: 화면
**지시**
- Next.js + TypeScript. `docs/fit_mockup.html`의 구성과 색 그대로.
- 화면 모드 라이트 / 다크 / 시스템(기본) 전환, 선택 저장, 그리기 전 적용 (Spec 6장).
- 입력창, 공고 목록(정렬, 라벨 필터, D-day, 재판정 필요), 공고 본문, FIT 진단 패널(조건 칩, 보류 인정, 요건 칩과 근거 태그, 선호 조건, 보완 포인트, 결정 버튼).
- 공고 원문은 반드시 이스케이프해서 표시 (`dangerouslySetInnerHTML` 금지).
- 분석 진행 중 단계 표시 (파싱 중, 판정 중 등).
